# 포트폴리오 작업 기록 — 항만 선박 정보 매칭 AI

> 대회: DACON 「항만 문제해결을 위한 AI 기술 공모전」 (해양수산부 주최, 울산항만공사·한국정보산업연합회 주관)
> 과제: 입출항 신고 기록 1행 → 표준 선박 제원 카탈로그(78,595척)에서 같은 선박 찾기 (개체 매칭, Entity Resolution)
> 지표: `0.7 × 한글 선박명 기록 정확도 + 0.3 × 비한글 기록 정확도` · 코드 제출형 (Python 3.11, L4 GPU, 추론 30분 제한, 인터넷 차단)

각 항목은 **작업 내용 → 결과 → 어려운 점 / 개선점 / 배운 점** 순서로 정리합니다.

## 1. 대회 분석과 데이터 탐색 (2026-10-22)

### 작업 내용
- 대회 페이지(개요, 규칙, 평가, 데이터 탭)에서 제약 조건 정리
  - **행 독립 원칙**: test의 다른 행이나 분포를 쓰지 못함. 셔플이나 부분집합으로 실행해도 예측이 같아야 함
  - 외부 데이터 금지, 범용 사전학습 가중치 허용
  - 하루 5회 제출, 실행 오류도 횟수 차감
- train(12,222행), 카탈로그(78,595척) 탐색
  - train의 한글 선박명은 **9.7%뿐인데 점수 가중치는 70%**. 카탈로그 선박명은 100% 영문
  - 한글 표기 예시: `모닝 닌니 → Morning Ninni`, `케이엠티씨 하이퐁 → KMTC Haiphong`, `티와이아이리스호 → TY Iris`
  - 비한글은 65%가 정규화 후 정확 일치. 나머지는 오타(`GLBAL TOMORROW`, `BBG CONFIDECNE`)
  - 총톤수는 카탈로그와 정확히 같은 경우가 약 50%, 대부분 ±5% 이내
  - `call_sign`(해시 처리된 호출부호)은 train 안에서 선박과 1:1 대응
- 공식 베이스라인(후보 검색 + RandomForest) 분석: 한글 기록은 후보 recall부터 68.6%에 그침

### 결과
- 문제를 **"한글 음역 매칭"과 "영문 오타 매칭" 두 갈래**로 분해하고, 점수 구조상 한글이 최우선임을 수치로 확인
- 전체 계획: [PLAN.md](../PLAN.md)

### 어려운 점 / 개선점 / 배운 점
- **어려운 점**: 대회 페이지가 탭별로 나뉘어 있고 일부 기준(본선 배점)은 이미지로만 제공되어 정보를 모으는 데 시간이 걸림
- **배운 점**: 데이터 비율(9.7%)과 점수 비중(70%)이 크게 다를 때는 **전체 정확도가 아니라 지표 구조를 기준으로 우선순위를 정해야** 함. 베이스라인의 비한글 98%는 개선 여지가 거의 없는 "착시"였음

## 3. 제출 패키지 자동 생성·검증 도구 (2026-10-22)

### 작업 내용
- [tools/make_submit.py](../tools/make_submit.py): 제출 폴더를 zip으로 묶고 서버와 같은 구조에서 실행해 검증
  1. zip 최상위 구조 검사 (상위 폴더가 끼면 서버 설치 오류)
  2. `requirements.txt`에 서버 기본 패키지가 있으면 경고
  3. 임시 폴더에 `data/test.csv`(train에서 정답을 뗀 표본)를 넣고 `script.py` 실행 → 출력 형식, 카탈로그 ID 여부, 실행 시간 검사
  4. 로컬 대회 지표 계산
  5. **행 독립성 자동 검사**: 셔플한 부분집합과 단독 행으로 다시 실행해 같은 예측인지 비교
- **검사기 자체를 검증**: test 행 수에 따라 예측이 바뀌도록 일부러 고장 낸 패키지로 실행 → "행 독립성 위반"으로 실패 처리되는 것 확인

### 결과
- 베이스라인 zip이 모든 검사를 통과 (1.04MB, 3,000행 4.6초)

### 어려운 점 / 개선점 / 배운 점
- **어려운 점**: 셔플 부분집합 검사만으로는 일부 위반을 놓침. 고장 낸 패키지(`len(test) % 50`)는 300행 부분집합에서는 우연히 통과했고 단독 행 검사에서 잡힘 → **검사를 여러 방식으로 겹쳐야** 함
- **개선점**: 로컬 실행에서는 인터넷 차단을 재현하지 못함 → LLM을 도입할 때 오프라인 로딩(`local_files_only=True`)을 별도로 검사할 예정
- **배운 점**: 규칙 준수(행 독립성)를 사람이 눈으로 확인하지 않고 **테스트로 자동화**하면 모델을 바꿀 때마다 안심하고 실험할 수 있음

## 5. 검증 체계와 1단계 후보 검색기 (2026-10-22)

### 작업 내용
- **공용 모듈** [src/common.py](../src/common.py): 데이터 로딩, 이름 정규화(NFKC, 대문자, 특수문자 → 공백), 한글 판별, 대회 지표
- **검증 fold** [src/validate.py](../src/validate.py): `StratifiedGroupKFold(5)`
  - 그룹 = `call_sign` (같은 선박은 한 fold에만 → 처음 보는 선박 상황을 재현)
  - 층화 = 한글 여부 (fold별 한글 비율 8.6%~11.1%)
  - 고정 seed로 `experiments/folds.csv` 저장 → 모든 실험이 같은 분할을 사용
  - recall@k 평가 함수 (한글, 비한글, 전체)
- **후보 검색기** [src/retrieval.py](../src/retrieval.py): 공식 카탈로그만 색인하고 질의 행마다 독립적으로 검색
  - `exact`: 띄어쓰기까지 지운 이름의 정확 일치
  - `tfidf_word`: 단어 경계를 살린 문자 2~4-gram TF-IDF (`char_wb`) → 단어 안의 오타에 강함
  - `tfidf_compact`: 띄어쓰기를 지운 문자 2~4-gram TF-IDF → 붙여쓰기·띄어쓰기 차이에 강함
  - `tonnage`: 총톤수가 가장 가까운 선박
  - 합집합: 위 결과를 정해진 순서로 합침. 동점은 카탈로그 행 번호로 정렬해 **결정적 결과** 보장

### 결과 (train 12,222행, 정답이 후보 k개 안에 들어가는 비율)

| 검색기 | 비한글 R@1 | 비한글 R@200 | 한글 R@1 | 한글 R@200 |
|---|---|---|---|---|
| 정확 일치 | 0.647 | 0.647 | 0.000 | 0.000 |
| TF-IDF (단어 경계) | 0.908 | 0.9985 | 0.003 | 0.026 |
| TF-IDF (띄어쓰기 제거) | 0.932 | 0.998 | 0.004 | 0.014 |
| 총톤수 근접 | 0.151 | 0.530 | 0.249 | 0.674 |
| **합집합 (후보 평균 157개)** | 0.914 | **0.9987** | 0.239 | **0.718** |
| (참고) 공식 베이스라인 후보 40개 | | 0.985 | | 0.686 |

- 비한글은 **TF-IDF만으로 1등 정확도 91~93%**, 후보 recall 99.87% → 놓친 정답이 1.5%에서 0.13%로 줄어듦
- 검색 속도 2.6ms/행 (색인 생성 2.6초) → 30분 제한에 충분한 여유
- 한글은 이름 검색이 거의 작동하지 않음 (영문 카탈로그와 문자가 겹치지 않음) → **한글→영문 변환이 필수**임을 재확인

### 어려운 점 / 개선점 / 배운 점
- **어려운 점**: 비한글에서 놓친 14행은 모두 **짧은 한 단어 + 글자 순서 바뀜 + 톤수 4~5% 오차**가 겹친 경우 (`SERAMLBER → Searambler`, `SUWNIN → Sunwin`, `HANAYNG → Hanyang`). 짧은 이름은 n-gram이 적어 순서가 한 번만 바뀌어도 유사도가 크게 떨어짐
- **개선점**
  - 글자 정렬 키(철자 순서와 무관한 키) 인덱스나 Damerau-Levenshtein 기반 보조 검색 추가
  - 톤수 검색을 "이웃 k개"가 아닌 **상대 오차 범위(±5%)** 로 바꾸기. 큰 선박은 ±5% 안에 수백 척이 있어서 k개로는 부족
  - 합집합 검색이 개별 검색 시간의 합과 비슷함 → 질의 벡터 변환과 행렬곱을 한 번에 처리해 최적화 여지 있음
- **배운 점**
  - 2단계 구조에서는 **1단계 recall이 최종 정확도의 상한**이라, 재순위 모델을 만들기 전에 recall부터 측정해야 함
  - 검증 분할을 **선박 단위로 묶지 않으면** 같은 선박의 다른 기록이 학습과 검증에 함께 들어가 점수가 부풀려짐 (선박당 최대 4행)

## 6. 2단계 재순위 모델: LightGBM LambdaRank (2026-10-22)

### 작업 내용
- **검색기 확장** ([src/retrieval.py](../src/retrieval.py) `generate`): 후보 인덱스와 함께 검색 신호(TF-IDF 코사인 2종, 검색기별 순위, 정확 일치 여부)를 돌려줌. 질의 행 벡터와 카탈로그 행렬의 곱이라 다른 행의 영향을 받지 않음
- **쌍 특징 41개** ([src/features.py](../src/features.py)): 질의 1행과 후보 사이
  - 이름: rapidfuzz `ratio`/`partial`/`token_sort`/`token_set`/`WRatio`, Jaro-Winkler, Levenshtein, **Damerau-Levenshtein**(글자 순서 바뀜 대응), 접두·접미 일치, 길이 차이, 철자 정렬 키 일치, 숫자 일치
  - **그룹 내 상대값**: 같은 질의의 후보 중 유사도 순위, 1등과의 차이 (같은 질의 안에서만 비교하므로 행 독립 원칙에 맞음)
  - 톤수: 총톤수·국제총톤수 상대 오차, 로그 비, 정확 일치, 결측 여부, DWT/GT 비
  - 범주: **한글 선종·국적 → 카탈로그 영문 범주 조건부 확률** `log P(영문|한글)` (`CategoryMapper`, 라플라스 평활)
- **학습** ([src/train_ranker.py](../src/train_ranker.py)): 질의 1행 = 그룹 1개, 정답 1개와 오답 후보 약 156개
  - 선박 단위 5-fold로 OOF 평가. 범주 매퍼는 **fold마다 학습 fold로만 다시 적합** (정답 정보 누수 방지)
  - 후보와 특징은 한 번 만들어 캐시하고, fold마다 범주 열만 다시 계산 → 실험 반복 시간 단축
- **제출 패키지 조립 자동화** ([tools/build_package.py](../tools/build_package.py), [tools/script_template.py](../tools/script_template.py)): 같은 코드로 두 가지 패키지 생성
  - `v1_hybrid`: 한글은 베이스라인, 비한글은 새 모델 → **Public 변화량으로 원인을 분해하는 실험용**
  - `v2_rank`: 모든 행을 새 모델로 예측

### 결과 (선박 단위 5-fold OOF)

| 모델 | 점수 | 한글 | 비한글 |
|---|---|---|---|
| 공식 베이스라인 (RandomForest) | 0.472 | 0.254 | 0.980 |
| **LambdaRank (반복 150 고정)** | **0.589** | **0.413** | **0.998** |
| (참고) early stopping 사용 | 0.606 | 0.438 | 0.998 |

- 비한글 오답이 2.0%에서 0.2%로 **약 10분의 1**로 줄어듦
- 한글은 이름 매칭 없이 톤수·선종·국적만으로 0.254에서 0.413으로 상승 (선종·국적 매핑 특징의 효과)
- 중요 특징(gain): `dl_rank_in_group` ≫ `dl_norm` > `fz_ratio` > `igt_gap` > `sim_compact_gap_to_best` > `flag_logp`, `type_logp`
- 두 패키지 모두 검증 통과. 3,000행 약 14.5초, zip 0.42MB(v2) / 1.46MB(v1)

### 어려운 점 / 개선점 / 배운 점
- **어려운 점 1 — early stopping의 함정**: 처음에는 검증 fold로 early stopping을 해서 OOF 0.606이 나왔지만, fold별 최적 반복 수가 2~112로 크게 흔들림. 반복 수를 고정하자 0.589로 떨어짐 → **검증 fold로 반복 수를 고르면 그 fold 점수가 부풀려짐**. 특히 한글 382척처럼 작은 집단에서는 노이즈를 "최적"으로 고르게 됨. 반복 수 고정으로 바꿔 정직한 수치를 기준으로 삼음
- **어려운 점 2 — 학습 데이터 채점의 착시**: v2를 train 표본으로 채점하면 0.782 (한글 0.689)지만 OOF는 0.589. 범주 매퍼와 트리가 train 선박을 외우기 때문 → **로컬 제출 검사 점수는 형식 확인용일 뿐 성능 지표로 쓰면 안 됨**
- **실험 결과**: 한글 행 가중치를 3배로 높여도 개선되지 않음 (한글 행의 정보가 톤수·범주뿐이라 가중치로 해결할 문제가 아님)
- **개선점**
  - 한글은 결국 **이름 신호(음역)** 가 필요함 → 다음 단계
  - 한글·비한글은 쓸 수 있는 신호가 완전히 달라서, 나중에 **모델을 분리**하는 것도 검토
  - 특징 생성 4.4ms/행 중 대부분이 TF-IDF 행렬곱 → 질의를 배치로 묶은 희소 연산 최적화 여지
- **배운 점**
  - LambdaRank에서는 **그룹 내 상대 특징**(이 후보가 같은 질의의 후보 중 몇 등인가)이 절대 유사도보다 훨씬 강력함 (gain 1위, 2위의 5배)
  - 제출 기회가 제한된 대회에서는 **제출 자체를 통제된 실험으로 설계**할 수 있음. 한 번에 한 부분만 바꾼 두 제출로 Public 점수 하나를 두 요소로 분해

  - 대소문자가 섞인 이름 속 대문자 약어(SITC, KMTC)는 **알파벳 읽기 키**로 변환 (`C → 씨 → S`)

- 규칙을 반복 개선한 과정 (train 한글 382척 기준, 압축 키 정확 일치율)

### 어려운 점 / 개선점 / 배운 점
- **어려운 점 1 — 규칙 간 충돌**: 한 사례를 고치는 규칙이 다른 사례를 깨뜨림. "모음 사이 S → ㅈ"(Sunrise → 선라이즈)은 Pegasus(페가서스), Boshi(보쉬: SH → S 다음에 다시 S → J)를 깨뜨려서, 적용 범위를 어말 SE로 좁힘. **규칙을 바꿀 때마다 전체 일치율을 다시 재는 회귀 테스트**가 필수였음
- **어려운 점 2 — 규칙 적용 순서**: `GH → ""` 규칙이 `NG` 규칙보다 먼저 적용되어 `Shanghai`의 `NGH`에서 G와 H가 사라지는 버그. 정규식 치환 체인에서는 순서가 곧 의미
- **어려운 점 3 — 셸 따옴표**: 큰 패치 스크립트를 heredoc 안의 `python -c`로 실행하다가 따옴표가 깨져서 아무것도 적용되지 않음 → 편집 도구로 파일을 직접 수정하는 방식으로 전환
- **주의 (평가 낙관 가능성)**: 발음 규칙은 train 한글 382척 전체의 실패 사례를 보면서 다듬었으므로, OOF 한글 0.966에는 **규칙 설계 단계의 누수**가 일부 섞여 있음. 규칙 자체는 일반적인 음운 대응이지만, test에서는 이보다 낮을 것으로 예상
- **개선점**
  - 남은 오답은 대부분 **발음 골격이 같은 다른 이름**(`Catherine ↔ Carina`, `Alliance ↔ Reliance`, `Feng Xiu Hai ↔ Feng Shou Hai`) → 모음 정보가 필요. 모음 키 추가 또는 LLM 음역으로 보완
  - 모호한 규칙(TH → T/S, G → K/J)은 하나로 정하지 말고 **여러 변형 키 중 최댓값**을 쓰는 방식 검토
- **배운 점**
  - 데이터가 적을 때(382쌍)는 학습 모델보다 **도메인 지식(외래어 표기 음운 대응)을 담은 규칙**이 훨씬 효율적임. 학습 없이 한글 정확도가 0.41에서 0.97로 오름
  - 규칙 기반 표현을 **최종 판단에 쓰지 않고 검색 신호와 특징으로만** 넣으면, 규칙이 틀려도 재순위 모델이 톤수·선종과 함께 보정해 줌

## 9. CV와 Public 차이의 원인 찾기: 스트레스 테스트 (2026-10-22)

### 작업 내용
- v3 제출 결과 **Public 0.7408** (v2 대비 +0.243). 비한글은 v2와 같으므로 변화량은 대부분 한글 → test 한글 정확도 약 **0.63**. 교차검증 0.966과 큰 차이
- 제출 없이 원인을 찾기 위해 **스트레스 테스트** 도구 작성 ([src/stress.py](../src/stress.py))
  - 검증 fold의 한글 기록에 test에서 있을 법한 변형을 가하고 정확도 하락을 측정
  - 변형은 대회 설명의 노이즈 목록("철자 변형, 약칭, 톤수 오차, 정보 누락")을 근거로 설계: 톤수 결측, 톤수 ±5% 오차, 국적 결측, 띄어쓰기 제거, 모음 오타(ㅐ↔ㅔ 등), 음절 탈락·중복, 단어 생략
- 데이터에서 단서 발견: **train 한글 기록은 총톤수 결측이 0%** (비한글은 7.2%) → 톤수 없는 한글 기록이 test에 몰려 있을 가능성

### 결과 (증강 전 v3 모델, 한글 1,191행)

| 변형 | 후보 recall | 정확도 | 하락 |
|---|---|---|---|
| 원본 | 0.988 | 0.966 | |
| **총톤수 결측** | 0.935 | **0.539** | **-0.43** |
| **단어 생략 (약칭)** | 0.825 | **0.441** | **-0.53** |
| 음절 탈락 | 0.903 | 0.782 | -0.18 |
| 톤수 ±5% | 0.940 | 0.888 | -0.08 |
| 국적 결측, 모음 오타, 띄어쓰기 제거, 음절 중복 | 0.98~0.99 | 0.95~0.96 | 작음 |

- **총톤수가 없으면 정답이 후보에 있어도 1등으로 고르지 못함** (recall 0.935, 정확도 0.539). 학습 데이터의 한글 기록에 항상 톤수가 있어서, 모델이 "이름만으로 고르는 법"을 배우지 못했기 때문
- 약칭은 후보 검색 단계부터 실패

- **배운 점 1**: 리더보드 점수는 숫자 하나지만, **가설을 세우고 검증 데이터에 그 가설의 변형을 재현**하면 제출 없이도 원인을 좁힐 수 있음
- **배운 점 2**: "train에서 항상 존재하는 정보"는 모델이 무조건 의존하게 됨. **학습 분포에서 결측 패턴이 test와 다를 수 있다**는 점을 데이터 탐색 단계에서 의심했어야 함 (한글 기록 톤수 결측 0%는 초기 탐색에서 놓친 신호)

## 10. 학습 데이터 증강과 약칭 대응 검색 (2026-10-22)

### 작업 내용
- **노이즈 증강** ([src/augment.py](../src/augment.py)): train 행마다 노이즈를 입힌 복사본 생성 (한글 행당 4개, 영문 행당 1개, 총 15,795행)
  - 이름 노이즈 0~2개: 한글은 모음 오타·음절 탈락·음절 중복·단어 생략·띄어쓰기 제거, 영문은 글자 탈락·중복·순서 바뀜·단어 생략
  - 톤수: 40% 결측, 30% ±5% 오차 / 국적: 30% 결측
  - 증강 행은 **원본과 같은 fold에만** 들어가게 해서 검증 누수를 막음 (`origin` 열로 추적)
- **학습 코드 재구성** ([src/train_ranker.py](../src/train_ranker.py) `Context`): 원본·증강 행의 후보와 특징을 한 번만 만들어 캐시하고, fold 학습과 스트레스 테스트가 같은 코드를 공유
- **약칭 대응 검색**: 발음 키를 **단어 경계 문자 n-gram**으로도 색인 → 일부 단어만 남은 질의도 검색됨
- **특징 6개 추가**: 단어 단위 키 검색 점수·순위, **단어 포함률**(질의 단어 중 후보에 있는 비율, 후보 단어 중 질의에 있는 비율 → 약칭이면 앞은 1, 뒤는 1 미만)
- 버그 수정: 증강 행 중 이름과 톤수가 모두 사라져 후보가 0개인 경우 특징 생성 실패 → 빈 행렬 반환

### 결과 (한글 1,191행 스트레스 테스트, 정확도)

| 변형 | v3 (증강 없음) | 증강 | **증강 + 약칭 검색 (v4)** |
|---|---|---|---|
| 원본 | 0.966 | 0.972 | 0.966 |
| 총톤수 결측 | 0.539 | 0.837 | **0.856** |
| 단어 생략 | 0.441 | 0.695 | **0.723** |
| 음절 탈락 | 0.782 | 0.839 | **0.854** |
| 톤수 ±5% | 0.888 | 0.912 | **0.924** |
| 톤수 결측 + 단어 생략 | (recall 0.36) | 0.254 | **0.335** |

- 원본 교차검증은 v3와 같은 **0.976** (한글 0.966, 비한글 0.998) → 평소 성능은 유지하면서 강건성만 크게 개선
- 증강 복사본을 한글 행당 8개로 늘려도 4개와 차이가 없어 4개로 결정 (학습 비용 절반)
- 중요 특징에 `type_logp`(3위), `key_tok_cover_q`(5위)가 새로 올라옴 → 톤수가 없을 때 선종과 단어 포함률로 판단하는 법을 배움

### 어려운 점 / 개선점 / 배운 점
- **어려운 점**: 증강의 효과를 원본 CV로는 볼 수 없음 (원본 검증 행에는 노이즈가 없으므로). 그래서 **스트레스 테스트를 증강의 평가 지표로** 삼았음. 단, 스트레스 변형과 증강 변형이 같은 함수라서 "같은 노이즈로 학습하고 평가"하는 낙관이 있음 → 실제 test 노이즈와 얼마나 맞는지는 Public으로만 확인 가능
- **개선점**
  - "톤수 결측 + 단어 생략"은 후보 recall이 0.56 → 남은 단어가 흔한 단어(`모닝`, `글로비스`)면 본질적으로 모호함. 선종과 국적으로 좁히는 검색 추가 검토
  - 비한글 기록에도 같은 스트레스 테스트를 해서 test 비한글 쪽 위험도 점검
- **배운 점**
  - **데이터 증강은 "모델이 배우지 못한 상황"을 만들어 주는 도구**. 핵심은 test에 있을 법한 상황을 근거 있게 정의하는 것 (여기서는 대회 설명의 노이즈 목록)
  - 증강 행을 원본과 같은 fold에 묶는 것처럼, **증강 데이터도 검증 누수의 통로**가 될 수 있음

- **약칭의 본질적 모호성 측정**: 여러 단어로 된 선박명에서 한 단어를 지웠을 때, 남은 단어를 모두 포함하고 총톤수도 ±1% 이내인 카탈로그 선박이 2척 이상인 비율 = **31.8%**
  - 같은 회사의 **자매선**(`Morning Catherine` / `Morning Carina`, 총톤수 동일)이 원인

### 결과
- 약칭 시나리오의 정확도 0.75는 이론적 상한(약 0.8 이하)에 가까움 → **더 이상 투자할 곳이 아님**
- train 비한글에 약칭이 전혀 없으므로 test에도 약칭이 많지 않을 가능성이 높음
- 남은 test 한글 차이(0.76 vs CV 0.97)는 시뮬레이션한 노이즈로는 설명되지 않는 부분이 있음 → **train에 없던 표기 방식**(새로운 음역 관습, 비영어권 이름)일 가능성 → LLM 음역이 다음 후보

### 어려운 점 / 개선점 / 배운 점
- **어려운 점**: 스트레스 테스트는 "내가 상상한 노이즈"만 측정함. test에 실제로 어떤 노이즈가 있는지는 알 수 없어서, 모든 시나리오를 똑같이 중요하게 다루면 효과 없는 곳에 시간을 쓰게 됨 (v5가 그 사례)
- **개선점**: 시나리오별로 **이론적 상한**을 먼저 계산했다면 v5 실험을 하지 않았을 것. 개선 실험 전에 "이 문제가 원리적으로 풀 수 있는가"를 먼저 확인하는 습관
- **배운 점**
  - 실제 데이터의 노이즈 분포를 측정하면 시뮬레이션을 **현실적인 시나리오에 집중**시킬 수 있음 (예: train 비한글에 약칭 0건)
  - 정확도가 안 오를 때는 모델 탓 전에 **정보가 충분한가**(자매선처럼 입력만으로 구분 불가능한 경우)를 확인해야 함

- **어려운 점 2**: 배치 16 × 빔 4 = 64개 시퀀스가 긴 few-shot 프롬프트와 겹쳐 로컬 GPU 메모리 부족 → 배치를 줄이고 `expandable_segments` 설정
- **개선점**: 배치 1은 속도가 절반 → few-shot 접두부의 **KV 캐시 재사용**, 같은 이름 결과 캐싱(같은 입력이면 같은 출력이므로 행 독립성에 영향 없음)으로 속도 개선 가능
- **배운 점**
  - LLM을 파이프라인에 넣을 때는 정확도뿐 아니라 **결정성(같은 입력 → 같은 출력)** 을 반드시 검증해야 함. 배치 처리는 성능 최적화이지만 규칙 위반의 원인이 될 수 있음
  - 모델 크기보다 **데이터 도메인(한국어 외래어 표기)과의 적합성**이 더 중요했음

  - 노이즈 증강된 한글 이름 포함, 단어 생략된 쌍은 제외 (없는 단어를 지어내도록 학습되는 것을 방지)
  - fold 0 선박을 빼고 학습 → fold 0의 원본·노이즈 이름에서 few-shot 원본 모델과 비교
  - LoRA를 원본 가중치에 병합해 저장 → 서버에 `peft` 불필요. 학습된 모델은 few-shot 없는 짧은 프롬프트를 써서 추론도 빨라질 것으로 기대

### 중간 결과
- LightGBM 반복 수 300: hard 0.8376 (기준 0.8377과 동일)
- LoRA 학습 손실: 0.72 → 0.08 → 0.014 (3 epoch, 학습 쌍 1,619개, 약 6분)

### 어려운 점 / 개선점 / 배운 점
- **어려운 점 1 — RAM 부족**: LoRA 학습과 재순위 비교를 동시에 돌리자, 두 프로세스가 큰 특징 캐시와 가중치를 함께 올려 시스템 RAM(32GB)이 부족해짐 → 둘 다 `MemoryError`. GPU 작업과 CPU 작업이라도 **메모리 자원은 공유**한다는 점을 놓침. 순차 실행으로 바꾸고, 가중치 저장을 1GB 단위로 나눔
- **어려운 점 2 — 토큰화 불일치**: 채팅 템플릿 문자열에 이미 시작 토큰(BOS)이 있는데 토크나이저가 한 번 더 붙임. 학습(`tokenize=True`)과 추론의 입력이 달라질 수 있어, 파인튜닝 모델은 추론 때 특수 토큰을 다시 붙이지 않도록 맞춤
- **배운 점**: 지표가 포화되면 **새로운 평가 축**(여기서는 노이즈 강건성)을 만들어야 모델 개선을 구분할 수 있음

## 16. v6 결과 해석과 test 한글 노이즈 역추정 (2026-10-23)

### 작업 내용
- **v6 Public 0.8979** (v4 대비 +0.069, 서버 8분 8초). 비한글을 0.998로 두면 test 한글 ≈ 0.855 (CV 0.994와 여전히 큰 차이)
- **train의 실제 노이즈 측정**
  - 비한글: 35%가 글자 삭제(39%)·중복(32%)·순서 바뀜(29%) 1~2회, **단어 생략은 0건**, 개명 추정(예: `BOW MERCURY` → `Benten Galaxy`) 약 0.8%
  - 이름 노이즈는 **선박 단위**로 고정 (같은 선박의 여러 행은 같은 오타). 5,851척 중 이름 변형이 있는 선박은 6척뿐
  - 한글: 이름 오타 없음, 톤수 결측 0%, 톤수 오차 28.5% (대부분 -6%~+5%)
- **제출 기록으로 test 한글 구성을 역추정**: 제출 v2·v3·v4·v6의 Public 점수를 "모델별 스트레스 시나리오 정확도의 혼합"으로 놓고 비음수 최소제곱으로 풀었음
  - 결과: **원본 44%, 톤수 결측 14%, 단어 생략 23%, 둘 다 19%** (비한글 정확도를 0.97~0.998로 바꿔도 거의 같음)
  - 해석: v6의 남은 손실 대부분이 **약칭(단어 생략형) 행**에서 나옴. train에는 약칭이 전혀 없어서 CV가 이 약점을 보여주지 못했음

### 어려운 점 / 개선점 / 배운 점
- **어려운 점**: test 정답을 볼 수 없고 제출도 최소화해야 해서, 노이즈 구성을 직접 확인할 방법이 없음
- **배운 점**
  - 제출 하나하나를 "어떤 시나리오에서 몇 점인 모델"로 기록해 두면, **Public 점수 여러 개를 연립방정식처럼 풀어** 숨겨진 test 분포를 추정할 수 있음. 진단용 제출 없이도 개선 방향을 정할 수 있었음
  - 같은 선박의 여러 행이 같은 오타를 공유한다는 사실은 "노이즈가 행 단위가 아니라 선박 단위로 주입됐다"는 데이터 생성 과정의 단서. 증강도 이 구조를 따르는 것이 맞음

## 17. 약칭(단어 생략) 대응: 검색은 크게 개선, 정확도는 정보 한계에 막힘 (2026-10-23)

- **어려운 점 1 — 캐시 키 누락**: 특징 캐시 키가 특징 이름만 해시하고 있어서, 검색 방식만 바꾸면 **예전 후보로 만든 캐시를 조용히 재사용**할 뻔함 → 검색 버전을 키에 포함
- **어려운 점 2 — 난수열 보존**: 약칭 방식을 바꾸면 뒤따르는 오타 함수가 이름 길이에 따라 난수를 다르게 소비해 모든 증강 행이 바뀌었음(같은 이름 13.8%) → 원래 흐름은 그대로 두고 대체 방식만 별도 난수열로 다시 만들어 87%를 그대로 유지, LLM 재생성을 282개로 줄임
- **배운 점**
  - **recall 상승 ≠ 정확도 상승**. 후보에 정답을 넣어도, 그 후보를 다른 후보와 구분할 정보가 행에 없으면 소용없음. 개선 전에 "정보 한계(오라클 상한)"를 먼저 재 봤다면 시간을 아낄 수 있었음
  - test 구성 추정(16장) 기준으로 계산하면 test 한글의 현실적 상한은 약 0.865로, v6(0.855)와 차이가 작음 → 약칭 대응은 여기서 멈추고 다른 축을 찾는 것이 맞음

**최종 기본 설정** (단어 포함 검색 + 새 특징, 혼합 증강 없음): OOF 0.9953 (v6와 같음), hard **0.8388** (v6 0.8377). 오차 범위의 개선이라 단독 제출은 하지 않고 다음 개선과 묶기로 함

## 23. v7 이후 개선 방향과 검증 진단 (2026-10-26)

### 작업 내용

- 2:2:1:1의 개선 95% 탐색용 구간은 **[-0.0014, +0.0068]**이며 fold 5개 중 2개는 악화했다. few-shot 12척(한글 37행)을 제외해도 개선 방향은 유지된다. 같은 정답 선박이 여러 fold에 걸친 사례는 0척이다.
- 약칭+결측 1,191행 중 **검색 실패 28행 / 후보에 있는데 틀린 행 525행**. 한글 검색 실패를 전부 고쳐도 현재 testlike에서 최대 +0.0037이다. 후보 확장보다 후보 간 구별 특징을 우선한다.
- `drop_word()`가 한 단어 이름을 유지하기 때문에 약칭 세트의 **312/1,191행(26.2%)은 실제 이름 생략이 아니다**. 실제 생략 879행의 v7 정확도는 약칭 0.7361, 약칭+결측 0.3948이며, 전체 시나리오 평균은 각각 0.8010/0.5357이다.
- 톤수 결측일 때 LLM 정확 일치 후보가 유일하면 강제 선택하는 규칙은 testlike **0.8857**로 하락하여 기각했다. 단순 결측 분기 블렌딩도 0.9035로 고정 2:2:1:1보다 낮았다.
- 개요 문서의 다음 단계와 0.425의 의미, 평가 예외를 갱신했다. 모델 학습·LLM 생성·test 조회·패키지 변경·제출은 수행하지 않았다.

### 어려운 점 / 개선점 / 배운 점
- **어려운 점 — 정보 상한과 휴리스틱 점수의 혼동**: 기존 0.425는 특정 규칙의 정확도로 엄밀한 상한이 아니다. 또한 실제 생략 행과 변형이 일어나지 않은 행을 섞은 평균은 직접 비교하면 안 된다.
- **개선점 — 후보 생성 단계의 검증 예외**: `Context`의 검색 범주 매퍼는 전체 train으로 학습하고, fold별 `refresh_category()`는 이미 생성된 후보와 `rank_tok`을 바꾸지 않는다. 영향은 미측정이며, 독립 평가 경로 보강이 필요하다.
- **개선점 — 점수 캐시의 식별성**: 현재 점수 파일에는 후보 ID가 없어 후보 순서의 일치를 파일만으로 입증할 수 없다. 이번에는 공통 캐시 계보·크기 검사·v7 지표 재현을 확인했으며, 이후 점수에는 후보 ID와 버전 해시를 같이 저장하는 것이 좋다.
- **배운 점**: top1뿐 아니라 top2/top5와 검색 recall을 함께 보면 다음 실험이 검색인지 순위 학습인지 구분할 수 있다. 현재는 IDF 가중 포함률, 단어 순서, 빔별 지지, 자매선 내 톤수 구별력이 우선이다.
- **배운 점**: 행 1,191개는 한글 선박 382척의 반복 기록이다. 증강 행이나 반복 입항을 독립 표본으로 취급하지 않고 선박 단위로 불확실성을 계산해야 한다. 이미 선택에 사용한 평가 세트의 구간은 탐색용이라는 제한도 남는다.

| 영문 단어 생략 행 (hard, 남은 단어에 오타 없는 181행) vs 이상적 규칙 | 톤수 없음: 모델 0.330 / 상한 0.326, 톤수 있음: 모델 0.624 / 상한 0.495 | 없음 (모델이 이미 상한 이상) |
| 한글 단어 생략 + 톤수 결측 (이전 22장) | 모델 약 0.40 / 상한 0.425 | 약 0.02 |
| 톤수 결측·둘 다 시나리오 오답 중 "LLM 음역이 정답 이름과 정확히 같은" 경우 | 31건 중 4건, 537건 중 4건 | 8행 (점수 0.001 미만) |
| 기록의 국적 신뢰도 | 국적 있음 83.5%, 매핑된 국적 = 카탈로그 국적 77% | 자매선 구분 단서로 약함 (이미 확률로 사용) |

- 결론: 지금의 test 노이즈 가설(16장) 안에서는 **모든 유형이 정보 한계 근처**. 재순위·특징 추가로 얻을 수 있는 것은 0.001~0.003 수준

### 어려운 점 / 개선점 / 배운 점
- **배운 점**: "개선안 찾기"의 첫 단계는 아이디어 나열이 아니라 **오차 예산(어디서 얼마를 잃는지)과 각 항목의 상한**을 표로 만드는 것. 이 표가 있으면 시도할 가치가 있는 것과 없는 것이 바로 갈림

## 27. 목표 0.97과 리더보드 분석, call_sign 조회 패키지 준비 (2026-10-26)

### 작업 내용

  - 같은 대회 공개 저장소도 호출부호 조회를 세 번째로 중요한 특징으로 사용

  - 금지 사항은 외부 데이터, test의 다른 행 사용, 원본 식별정보 복원 → 해시를 풀지 않으므로 해당하지 않는 것으로 보임 (호출부호를 명시한 조항은 없음)
- **v9 패키지 준비** (`submit/v9_callsign`, 제출은 사용자 결정 후)
  - `tools/build_package.py --callsign-lookup`: train의 호출부호 → 선박 대응표(5,851개, 1:1 확인)를 넣음
  - 추론: test 행의 호출부호가 대응표에 있으면 그 선박, 없으면 v8 예측 그대로
  - 검사 통과 (행 독립성 OK, 156초). 호출부호를 모두 바꾼 3,000행에서는 v8과 같은 0.9996 → 없는 호출부호에는 영향 없음

### 어려운 점 / 개선점 / 배운 점
- **어려운 점**: 로컬 검증은 선박 단위로 fold를 나눠서 호출부호가 겹치지 않으므로, 이 신호의 효과를 로컬에서 잴 수 없음. test와 train이 선박을 공유하는지는 제출로만 알 수 있음
- **배운 점**
  - "정보 한계"라는 결론은 **내가 쓰는 입력 안에서의 한계**였음. 외부 기준(리더보드 상위 점수)과 크게 어긋나면, 결론보다 전제(어떤 입력을 쓰는가)를 먼저 의심해야 함
  - 검증 설계(선박 단위 fold)가 특정 신호를 원천적으로 볼 수 없게 만들 수 있음. 검증 방식 자체가 test 구조에 대한 가정임

- 판별기는 공식 범용 가중치의 리비전 `e61197ed45024b0ed8a2d74b80b4d909f1255473`을 고정했다. LoRA rank 8, alpha 16, 학습률 1e-4, 시드 42, 최대 256토큰이다. 학습 후보는 외부 검증 선박을 제외한 원본·증강에서 생성한다. 원격 Python이나 외부 선박 데이터는 받지 않았다.

### 어려운 점 / 개선점 / 배운 점
- **배운 점**: 추가 특징이 같은 후보를 공유한 기존 검증에서 단일 모델을 개선해도, 독립 검색 경로나 기존 최고 앙상블의 개선으로 이어지는 것은 아니다. 실제 비교 결과를 보고 채택해야 한다.
- **개선점**: 질의별 확률을 저장한 뒤 다시 softmax하면 블렌딩 의미가 달라진다. 2단계 모델 점수는 로그확률로 저장하도록 수정했고, 변환 전후 top1 불변을 확인했다.
- **개선점**: 대형 특징 행렬을 매번 읽지 않도록 후보 ID 메타데이터만으로 평가하는 `tools/blend_matching.py`를 추가했다.
- **배운 점**: 먼저 끝난 네 fold의 개선만으로 결론을 내리면 과장된다. 마지막 fold의 하락으로 전체 순증이 줄었고 신뢰 구간은 0을 포함했다. 모든 fold와 선박 단위 불확실성을 확인해야 한다.
- **배운 점**: 정답 회복과 새 오답을 함께 센다. testlike 변형은 111행 회복·93행 손실로 순증 18행이었다. hard는 53행 회복·39행 손실이다. 회복된 예시만 제시하면 실제 개선 폭을 과장하게 된다. [변화 집계](../experiments/neural_change_audit.json)
- **개선점**: LoRA 병합 전후 BF16 연산 차이가 있어 최종 검증과 배포를 병합 모델로 통일했다. 단독 CSV의 dtype 변화도 신경망 입력 토큰을 바꿀 수 있어 수치 표현을 정규화했다.

## 52. 원인 재점검과 v13_callsign 후보 준비 (2026-10-30, 미제출·사용자 결정 대기)

### 작업 내용

- Codex로 진행한 v12 이후 실험(10개 이상 계열)을 다시 검토했다. 모두 같은 가정(test 한글에 약칭·톤수 결측이 섞여 있음, 호출부호·동일 선박 조회 제외) 안에서 이름 판별을 개선하려는 시도였고, testlike 순증을 얻지 못했다.

- 공식 규칙 확인: "test.csv의 각 행은 해당 행의 입력값과 공식 제공 데이터만으로 예측", 금지 대상은 외부 DB·외부 정답/매핑표·다른 test 행 이용이다. 호출부호 조회 허용 여부를 묻는 공개 질문(talkboard 418273)에는 아직 운영진 답변이 없다.

## 53. v13 결과 해석 → train 선박 제외(v14) 준비 (2026-10-30, 미제출)

### 작업 내용

- **v13 결과:** Public 0.9065951735 / 10분 11초로 v12와 소수점 10자리까지 같았다. Public test에서 train 호출부호가 한 번도 적중하지 않았다는 뜻이다(선박 비중복이거나 익명화 방식이 다름). 상위권 0.98은 호출부호 조회로 설명되지 않는다.

- **train 선박 제외 probe:** test 선박이 train에 없다면 train 선박은 후보에서 빼도 된다. 선박 단위 CV에서는 "학습 fold 선박 제외"로 정확히 흉내 낼 수 있다. 저장된 v8 OOF 점수로 계산하면 testlike **0.9050 → 0.9239(+0.019)**, 단어 생략 0.809 → 0.877, 생략+결측 0.549 → 0.610, hard 0.846 → 0.863이고 원본 OOF는 그대로였다. 실제 test에서는 제외 목록이 학습 fold(약 4/5)가 아니라 train 전체라 효과가 조금 더 클 수 있다. ([도구](../tools/probe_exclude_train_vessels.py), [로그](../experiments/exclude_train_vessels_probe.log))
- **v14_exclude 패키지:** v12 + `model/train_vessels.json`(5,851척). 신경망이 상위 20개를 고르기 전에 기본 확률에서 train 선박을 0으로 만들고, 최종 선택에서도 제외한다. v12의 신경망 모듈은 소스 해시를 검사하므로 그 파일은 수정하지 않고 script.py에서 감쌌다.
- 검증: 스트레스 200척을 제외 목록에서 뺀 상태로 실행하니 v12 대비 손실 0, 회복 3(음절 탈락 0.940 → 0.955). make_submit 3,000행 223.6초, 행 독립성 통과, ZIP 6.65GB. train 행 점수가 0.0000인 것은 정답이 모두 제외 목록에 있어서 생긴 의도된 결과이고, 모든 행에서 제외가 작동했다는 확인이다.

### 어려운 점 / 개선점 / 배운 점

- 실패한 제출(v13)도 정보다. "점수 변화 없음"이 test 구조에 대한 강한 증거가 됐고, 이전에 금지 목록에 있던 "선박 중복" 계열을 반대 방향(비중복)으로 활용하는 아이디어로 이어졌다.
- 위험: test에 train 선박이 있는데 호출부호만 다르게 익명화된 경우라면 v14는 크게 떨어진다. v11 신경망(train 이름 학습)의 Public 상승폭이 선박 분리 CV 예측과 비슷했던 점도 비중복을 지지한다. 결과가 떨어지면 v12로 되돌리면 된다.

## 54. train 선박 제외 이후의 추가 개선 시도 (2026-10-30, 둘 다 보류·기각)

### 작업 내용

- **제외 이후 오답 분해**(v8 OOF, train 선박 제외 후): 톤수 결측 1,191행 중 오답 31, 단어 생략 오답 147, 생략+결측 오답 464행이었다. 대부분은 정답이 후보 안에 있지만 2~5위로 밀린 경우다(생략+결측: 2위 141, 3~5위 156, 6~20위 129, 후보 없음 28). 후보 검색보다 후보 안에서의 판별이 병목이다. ([도구](../tools/probe_exclusion_errors.py))
- **카탈로그 등장 확률(기각):** fold마다 카탈로그 속성(선종·국적·단위·크기·톤수·결측·이름 길이·카탈로그 위치)으로 "입항 기록에 나오는 선박인가"를 LightGBM으로 학습했다. 검증 fold 선박은 음성으로 처리해 test 상황과 맞췄다. 후보 점수에 a·전체 등장 + b·한글 등장 로짓을 더하는 5×5 격자에서 최고가 0.9239 → 0.9257(+0.0018)에 그쳤고, 원본 OOF를 깎는 설정이 많았다. 선택 편향을 감안해 기각했다. ([도구](../tools/probe_appearance_prior.py), [결과](../experiments/appearance_prior_probe.json))
- **test 맞춤 학습 그룹(보류):** 학습 그룹에서도 다른 학습 fold 선박을 빼서 "정답 대 train에 없는 선박" 비교만 학습시켰다. 평가는 둘 다 train 선박을 제외한 상태다. LightGBM 0.9154 → 0.9178(+0.0024, 세 시나리오 모두 소폭 상승, OOF 동일), GPU CatBoost 0.8993 → 0.8999(+0.0006)였다. 방향은 맞지만 폭이 작아, 마감 전에 v12 전체(CPU CatBoost 3개 + 신경망 2개)를 다시 학습할 근거로는 부족하다. ([도구](../tools/probe_exclusion_training.py), [결과](../experiments/exclusion_training_probe.json))

### 어려운 점 / 개선점 / 배운 점

- 큰 개선은 학습 기법이 아니라 test 구조에 대한 사실(선박 비중복)에서 나왔다. 그 사실을 반영하고 나면 같은 정보 안에서의 미세 조정은 다시 +0.002 수준으로 줄어든다.
- 남은 오답의 대부분은 약칭과 톤수 결측이 겹친 행이다. 이 행들에서 상위권 수준(0.98)이 나오려면 아직 찾지 못한 다른 정보가 필요하다.

## 56. 오타 + 톤수 결측 약점 발견 → 편집 거리 퍼지 검색(v15) (2026-10-30, 준비 완료)

### 작업 내용

- **약점 측정:** 학습 한글 200척 × 이름 변형 9가지를 **톤수를 모두 지운 상태**로 v14에 넣었다. 원본 0.995, 자모 오타 0.92, 음절 탈락 0.83, 음절 순서 바뀜 0.82였다(학습 선박이라 실제로는 더 낮을 것). 톤수가 있으면 0.94 이상이던 변형들이다.
- **원인:** 실패 114건 중 **76건(67%)은 정답이 후보 목록에 아예 없었다.** 오타가 발음 키와 LLM 음역을 함께 비틀고, 톤수가 없으니 톤수 검색도 못 쓴다. 놓친 행에서 검색기별 정답 순위를 재 보니 TF-IDF(LLM 음역)는 상위 20 안에 19건, **LLM 음역 ↔ 카탈로그 이름의 Indel 편집 거리 유사도는 64건**이었다.
- **v15_fuzzy:** 한글 질의마다 (발음 키 ↔ 카탈로그 키), (LLM 음역 4개 ↔ 카탈로그 이름)의 Indel 유사도 상위 20개씩을 후보에 추가한다. 새 후보의 순위 신호는 "목록 밖(999)", 유사도는 기존과 같은 방식으로 계산해 넣어서 순위 모델을 다시 학습하지 않았다. retrieval.py는 해시 검사 대상이라 script.py에서 감쌌다.
- **검증(v14 대비, 같은 4,200행):** 회복 44, 손실 1. 톤수 없음 기준 자모 오타 0.920 → 0.965, 음절 순서 0.820 → 0.865, 음절 탈락 0.830 → 0.860, 음절별 띄어쓰기 0.940 → 0.970. 톤수 있는 원본 등 쉬운 경우는 손실이 없었다. make_submit 3,000행 231.1초(v14 224초), 행 독립성 통과, ZIP 6.65GB.
- **사고 기록:** 첫 make_submit 두 번이 access violation으로 실패했다. faulthandler로 추적해 보니 LLM 가중치를 읽다가 죽었고, 원인은 **C: 드라이브 여유 공간 부족(189MB)**으로 ZIP 압축 해제가 잘린 것이었다. 임시 폴더를 D:로 지정해 해결했다. ZIP 무결성(testzip)은 처음부터 정상이었다.

### 어려운 점 / 개선점 / 배운 점

- testlike의 "단어 생략" 중심 가정 때문에, 실제로 더 흔할 수 있는 "오타 + 톤수 결측" 조합의 약점이 그동안 측정되지 않았다. 측정할 시나리오를 바꾸자마자 개선 지점이 보였다.
- 재학습 없이 후보만 늘리는 방식은 마감 직전에 위험이 작다. 순위 모델이 이미 오타 증강으로 학습돼 있어, 정답이 후보에 들어오기만 하면 상당수를 맞힌다.
- 로컬 실패 원인을 코드에서 찾기 전에 환경(디스크 공간)부터 확인해야 한다.

- **v18_fuzzy500** = v17에서 `FUZZY_K` 200 → 500. make_submit 3,000행 248.7초, 행 독립성 통과, ZIP 6.65GB. 로컬 평가 선박은 LLM 음역이 거의 정확해 후보 확대 효과가 로컬에서 드러나지 않는다(20 → 50 → 200 모두 로컬 미미, Public 각 +1%p). 그래서 중립 결과를 감수하고 채택했다.
- 실험이 도는 동안 v17 폴더의 train 선박 목록이 평가용 축소판(5,469척)으로 잠시 바뀌어 있었고, v18 폴더가 그 상태로 복사됐다. 바로 발견해 전체 목록(5,851척, train과 집합 일치)으로 되돌렸다. 교훈: 패키지 파일을 임시로 바꾸는 실험과 패키지 복사를 동시에 하지 않는다.
